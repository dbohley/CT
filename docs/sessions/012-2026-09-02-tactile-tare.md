# 012 — 2026-09-02 — tactile-tare

## Goal

Contact was firing on the very first sensor sample of every run (`contact_t` ≈ 0.0002 s), so
APPROACH never ran and everything downstream measured from a datum that was never established.
It had been an occasional annoyance — once every 5–10 runs — and became every run.

## What changed

**The tactile sensor is tared at the start of every run.** Before any motion is commanded,
`run_approach_and_seat.py` samples the reading for `--tare-s` (2.0 s, ~200 samples) with the
base stationary and takes the mean as this run's zero. Contact then means deflection from
where the arm actually rests today, rather than from a firmware zero set at some boot hours
earlier.

The subtraction happens on the **signed** `dist_cm` before the magnitude is taken —
`abs(dist_cm - zero) * 10` — because `dist_cm`'s sign is documented as arbitrary and the
deflection that matters is in either direction. Taking the magnitude first would fold a
negative rest position onto a positive one and get the tare wrong.

Applied to all downstream logic, not only the contact test: seat's amplitude window and
standoff's settled peak are deflection measurements too, and both were tuned when the drift
was 0.005 mm, so taring everywhere is what preserves their intent. The 0.1 mm threshold is
unchanged and now sits 7–50 σ above the measured noise instead of inside a drifted offset.

**Two bugs in session 011's phantom code, found by reading the newly-captured stdout.**

- `read_fresh_position_rad` replaces a naive read for the post-`SET_ORIGIN` check.
  `bus.recv()` returns the **oldest** queued frame, and after the 0.5 s settle at ~51 Hz there
  are ~25 pre-command frames ahead of the one that matters — so the check was deciding on a
  position from *before* the origin was applied. Run `20260902-154504` refused on exactly
  that (pre-zero −0.2321 rad, "readback" −0.2286 rad), and that refusal was a false alarm.
- The `disable` frame is now sent from the `finally`, and a Ctrl+C anywhere exits cleanly.
  Previously the handler wrapped only the playback loop, so an interrupt during either ramp
  escaped, skipped the disable, and left the motor holding position with a traceback on
  screen — visible in both runs at 15:45.

## Decisions and rationale

**Tare rather than raise the threshold.** The reading is clean — std stayed at
0.002–0.014 mm across two days — so the problem is entirely a moving datum. Raising the
threshold to clear the drift would have desensitised real contact detection 5× and bought
only time, since the drift continues.

**Warn, do not refuse, when the arm looks already in contact.** A tare taken while the arm is
genuinely pressed zeroes out real contact, and the base then drives in from an already-loaded
state. The discriminator is reliable — a free arm shows p2p 0.014–0.10 mm over the window, an
arm riding the breathing phantom shows 0.808 mm, an 8–60× separation — so the run says so
loudly and continues. Chosen deliberately; the operator is the check.

**A dead sensor does refuse.** Zero samples in the tare window is a different failure: nothing
the run measures could mean anything. Raised as `SetupFailed` so it unwinds through the same
`finally` that de-energises the motor and still reaches the summary.

## Findings

- **The tactile firmware zero drifts ~0.008 mm/hour, and the reading itself is clean.**
  0.0048 mm at rest on 2026-09-01 16:54, 0.1967 mm on 2026-09-02 15:46 — a 40× creep — while
  std stayed at 0.002–0.014 mm. Any absolute threshold on this signal has a shelf life; the
  0.1 mm one lasted about two days. Within a run the drift is ~0.0004 mm, so a per-run zero
  is sufficient and a mid-run re-tare is not needed.
- **The failure was silent and looked like success.** A run that declares contact at t=0.0002 s
  reports `phase_reached: seat` with no fault, and only the absence of an `approach` phase in
  the log gives it away. Anything derived from such a run — seating depth, standoff, the
  42.7 mm the base drove in run 151454 — was measured from a datum that was never established.
- **Capturing the phantom's stdout paid for itself on the first run after it was added.** Both
  session-011 bugs above were found by reading `phantom/stdout.log`; neither is visible in the
  JSONL or the summary. Diagnostics that only reach the terminal are diagnostics you do not
  have.
- **`bus.recv()` returns the oldest queued frame, which makes "read back what just changed" a
  trap.** Any check of the form "command something, then read to confirm" on this bus has to
  flush first. Worth remembering wherever else the pattern appears.

## Open questions

- **Why is the zero drifting at all?** Thermal, encoder creep, or the arm's mechanical rest
  position shifting. The tare makes it harmless for contact detection but it is still an
  uncharacterised instrument, and a large enough excursion could exceed the arm's range.
- **Does `SET_ORIGIN` actually work on this firmware?** Session 011's readback check could not
  answer it because it read stale frames; with the fix, the first hardware run will.
  Both runs where it appeared to "succeed" had the motor already at ~0, so the check passed
  trivially.
- Carried: in-contact `R`, whether `tau_s = 0.677 s` is a constant, Q as the NIS suspect,
  approach travel needed for a seated contact, standoff having no distance bound, and the
  42.7 mm standoff drive observed in session 011.
